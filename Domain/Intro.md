# Domain. Intro
Перед началом работы над клиентским веб-приложением важно понимать, какими сущностями будет оперировать наш фронтенд.

Выделение отдельного слоя для описания всех сущностей предотвращает их дальнейшее протекание в остальные части приложения.

## Проблема
Например, часто можно увидеть следующий кейс:

```typescript
// src/components/LoginForm.tsx

type UserCredentials = {
    password: string;
    login: string;
}

interface LoginFormProps {
    onLogin: (user: UserCredentials) => void;
}

export const LoginForm = ({ onLogin }: LoginFormProps) => {
    const handleOnSubmit = ({ login, password }) => {
        const userCredentials: UserCredentials = {
            login,
            password
        }

        onLogin(userCredentials);
    }

    return <Form onSubmit={handleOnSubmit}>
        <Input />
        <Input />
    </Form>
}
```
В  файле `LoginForm.tsx` мы описали тип, с которым работает наш компонент. UI, тайпинги, обработчики событий формы - все в одном месте. Вроде удобно на первый взгляд.

Тем не менее, `UserCredentials` в дальнейшем явно будет всплывать в родительских компонентах и ни раз:
* Наше API должно знать данный тип для типизации payload при запросе к эндпоинту.
* Родительский компонент тоже должен быть в курсе, какими полями обладает объект, принимаемый пробрасываемым коллбеком `onLogin`
* В свою очередь, `onLogin` в родительском компоненте может сохранить данные в стор приложения, что также является поводом сделать доступным тип `UserCredentials` в месте объявления этого стора 
* P.S. (тем не менее, в примере с пользовательскими данными авторизации в стор сохранять их лучше не стоит)

Также стоит упомянуть, что использование печально известной "палочки-выручалочки" в виде `export` перед `type UserCredentials` и последующий импорт типа в названные выше компоненты в конечном счете выручит лишь вашего тимлида, когда ему нужно будет отругать вас при очередном code-review.

И тимлид будет прав, ведь если мы построим диаграмму зависимостей наших файлов при экспорте типа из `Login.tsx`, то увидим следующее:

```
                    ┌──────────────────────┐                            
      ┌─────────────► components/Login.tsx ◄───────────────┐            
      │             └──────────────────────┘               │            
      │                                                    │            
      │                                                    │            
┌─────┼───────────┐                          ┌─────────────┼───────────┐
│ api/auth.api.ts │                          │ components/AuthPage.tsx │
└─────────────────┘                          └─────────────────────────┘
```
Решительно не понятно, почему слой API знает о существовании компонента `Login.tsx`. В свою очередь, `AuthPage.tsx` как страница тоже на троечку, ведь сам факт использования слова "страница" предполагает, что мы будем собирать ее из разных виджетов и компонентов, а не импортировать по частям как Typescript-Франкенштейна. 

Компонент `Login.tsx` должен подключаться целиком как обособленный и логически завершенный модуль, то есть стрелочка на диаграмме должна быть в другую сторону. В ином случае, изменение в компоненте, стоящем ниже по иерархии, затронет компонент выше, а это никак не должно быть.

## Решение

Правильным действием будет поместить тип в `UserCredentials` в место, откуда все прочие компоненты смогут его импортировать равнозначно. В нашем случае решением может стать `src/domain/user.ts`. Таким образом, получим следующую картину:
```typescript
// src/domain/user.ts

export type UserCredentials = {
    password: string;
    login: string;
}
```
```typescript
// src/components/LoginForm.tsx
import type  { UserCredentials } from "@/domain/user"

interface LoginFormProps {
    onLogin: (user: UserCredentials) => void;
}

export const LoginForm = ({ onLogin }: LoginFormProps) => {
    const handleOnSubmit = ({ login, password }) => {
        const userCredentials: UserCredentials = {
            login,
            password
        }

        onLogin(userCredentials);
    }

    return <Form onSubmit={handleOnSubmit}>
        <Input />
        <Input />
    </Form>
}
```
В итоге диаграмма импортов в проекте будет выглядеть следующим образом:
```
                       ┌────────────────┐                               
        ┌──────────────► domain/user.ts ◄──────────────────┐            
        │              └───────▲────────┘                  │            
        │                      │                           │            
        │                      │                           │            
┌───────┴─────────┐ ┌──────────┴───────────┐ ┌─────────────┼───────────┐
│ api/auth.api.ts │ │ components/Login.tsx │ │ components/AuthPage.tsx │
└─────────────────┘ └──────────────────────┘ └─────────────────────────┘
```

А это уже другое дело. Так как доменный слой - ядро всего приложения, фундамент и самая настоящая база, остальные слои, будь то API, UI или, скажем, аналитика, могут и должны зависеть от ядра.
